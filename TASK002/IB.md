### I. Идентификация и аутентификация, управление доступом

Так как одна управляющая компания видит данные другой, это говорит о проблемах с управлением доступом.
Баги, из-за которых у пользователя есть возможность увидеть чужие данные (ФИО), очень критичны. Нужен контроль для потоков данных между сервисами. 
Эти проблемы говорят о том, что управление доступом - это приоритетное направление для улучшения системы.
Раздел позволяет проверить, используются ли надёжные механизмы идентификации, как обеспечивается защита учётных данных и можно ли отследить подозрительные действия

### II. Активы

Организация располагает множественными distributed services и API endpoints без централизованного asset inventory и entry point mapping. Data flows между микросервисами не имеют proper governance, отдельные сервисы содержат redundant datasets. Требуется провести IT asset discovery и data classification для определения data processing scope каждого компонента и установления access control matrix. В архитектуре присутствует fragmented microservices landscape с отсутствием CMDB и API gateway visibility. Internal data pipelines лишены DLP controls, наблюдается data sprawl в отдельных service domains. Необходим comprehensive asset audit и data mapping для понимания data lineage, processing boundaries и implementation RBAC policies.

### III. Журналирование и мониторинг

Observability системы критически важна. Без неё incident response затруднен или невозможен, а клиенты первыми сталкиваются с проблемами. Transparency, logging и alerting также являются приоритетом для повышения SLA. Auditability ИС имеет критическое значение. Отсутствие observability усложняет forensic analysis инцидентов, что приводит к customer-first error detection. Visibility, централизованный logging и real-time alerting - ключевые факторы для улучшения QoS.

### IV. Защита данных

Организация обрабатывает персональные данные (PII - Personal Identifiable Information), транзакционные данные (transaction data), данные о бенефициарах (beneficial ownership data), интегрируется с государственными API (government APIs) — все категории требуют защиты данных (data protection).
Кроме того, в описании указано, что межсистемный обмен данными (inter-system data exchange) происходит без ограничений доступа (access controls), а партнерские интеграции (third-party integrations) не соответствуют требованиям безопасности (security requirements).
Необходимо провести аудит соответствия (compliance audit) требованиям ФЗ-152 (Federal Law 152-FZ) для предотвращения административных штрафов (regulatory penalties).

### V. Работа с партнерами

Организация использует внешние API управляющих компаний (third-party management company APIs), однако отсутствуют стандарты безопасности интеграций (integration security standards) и политики работы с партнерами (partner security policies). Зафиксированы инциденты избыточных привилегий (excessive privileges) в партнерских точках доступа (partner endpoints), нарушающие принцип минимальных прав (principle of least privilege). API-контракты (API contracts) содержат категории данных с явной передачей ПДн (PII exposure), что представляет нарушение требований ФЗ-152 (Federal Law 152-FZ compliance violation) и влечет риски регуляторных санкций (regulatory penalties).
